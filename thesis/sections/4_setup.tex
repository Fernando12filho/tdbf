\section{Experimental Setup}
\label{sec:setup}

\subsection{Dataset and Sample}
\label{sec:exp-dataset}

We evaluate on SWE-bench Lite~\cite{Jimenez2023SWEbench}, a 300-instance
subset of SWE-bench drawn from 12 Python repositories. The subset is uneven:
django contributes 114 instances and sympy 77, while flask contributes three.
We chose Lite over SWE-bench Verified because both use the same harness and
scoring, and Lite costs less per data point, which mattered once the study had
to run on free model endpoints (Section~\ref{sec:exp-budget}).

We developed the system on 14 Lite instances: all six astropy instances and
eight early django instances. This development set was not drawn at random, so
it is excluded from the evaluation sample, and the results we report on it are
pilot evidence that is never pooled with the sweep.

The evaluation sample was drawn and committed to the repository on 17
September 2026, before either arm ran on it, together with its analysis rules
(\texttt{sample\_lite\_frozen.json}). It holds 60 instances drawn with seed
20260916, stratified by repository with proportional allocation over the 286
instances outside the development set: django 22, sympy 16, matplotlib 5,
scikit-learn 5, pytest 4, sphinx 3, and one each from requests, pylint, xarray,
seaborn, and flask. Because the development set holds every astropy instance,
the sample contains no astropy. The request budget set the size. One paired
instance took 62 model calls in a live check, and the free tier allows 1,000
calls a day, which comes to about 16 pairs per day over the week available for
the sweep.

A pre-registered rule excludes an instance before any arm runs if its Docker
image cannot be built or its reference patch does not resolve in our harness.
The rule is applied from the reference-patch check alone, never from agent
results. Fifty-five of the 60 instances passed it. Four more
(matplotlib-25332, matplotlib-25498, sphinx-7686, sphinx-8801) had no working
image by the start of the sweep, because of disk space and, for the two sphinx
instances, an image build we interrupted ourselves. These four are not invalid
under the rule, so we report their absence as a departure from the protocol.
The fifth, django-14730, has a valid environment, but four consecutive
attempts failed on provider overload errors (HTTP 503) and it was never scored.
We report it as attempted and incomplete. The sweep therefore covers 55
instances.

\subsection{Model and Arms}
\label{sec:exp-arms}

Every RQ1 run uses a single model,
\texttt{nvidia/nemotron-3-super-120b-a12b}, served free through OpenRouter.
It is a mixture-of-experts model with 120B parameters, of which 12B are active
per token.

We chose it with a capability probe on the development set, which never
touches the sample. Of the other candidates, \texttt{gemma-4-31b-it}'s first
attempt failed on shared-pool rate limits and \texttt{nemotron-3-ultra-550b} timed out on a
single tool call. On three astropy instances, nemotron-3-super had all three
of its tests accepted, all three at level L4, and resolved one issue, without
a single throttling event. That was enough to rule out the outcome in which
both arms resolve nothing and the comparison says nothing. Free endpoints can
change without notice, so every record stores the model id and the provider
that served it.

The test-first arm (Arm B) is the deployable pipeline of
Section~\ref{sec:approach}. The reactive arm (Arm A) is the baseline of
Section~\ref{sec:method-baseline}: the same fix agent with the same prompt,
minus \texttt{run\_brt} and with no test phase. Both arms run in the same
container image and are scored by the same harness, under the budgets in
Table~\ref{tab:exp-config}. The per-turn cap is large because this model
reasons at length before it calls a tool, and free endpoints offer no prompt
caching.

The budgets are matched per agent run. Arm A makes one run per instance.
Arm B makes a test run of up to three attempts and, if the gate accepts, a
fix run. Arm B can therefore spend more calls on an instance than Arm A. This
asymmetry comes with the treatment, since the test phase is what is being
tested, and we report calls per instance for both arms so the reader can weigh
it. When the gate rejects, Arm B counts as not resolved. A rejection is the
pipeline declining to fix, and dropping those instances would compare Arm A on
every instance with Arm B on the ones it found easier.

The driver was built to run both arms back to back on each instance, in a
seeded random order, so that any drift in a free endpoint would affect both
arms alike. The sweep did not run that way. Arm B ran first, over all 55
instances, from 21 to 24 September 2026. Arm A then ran as a separate pass over
the same instances in a seeded random order (seed 20260916), starting on 25
September, and completed \ph{N} of them.

\subsection{Measures and Analysis}
\label{sec:exp-metrics}

The primary outcome is whether an instance is resolved: every held-out
FAIL\_TO\_PASS test passes and no PASS\_TO\_PASS test breaks
(Section~\ref{sec:method-levels}). We score each patch with the unmodified
SWE-bench harness under a fresh run id and accept a verdict only if its report
was written by that call and records the patch we submitted. Any other verdict
is treated as a scoring error and excluded. The check exists because the
harness skips an instance whose report already exists under the same run id:
with a fixed id, re-runs silently inherited old verdicts, and we re-scored the
20 affected verdicts before this study.

The analysis was fixed in the sample file before the sweep. RQ1 compares the
arms with McNemar's exact two-sided test on the discordant pairs, together
with a paired bootstrap 95\% confidence interval (10,000 resamples) for the
difference in resolved-rate, test-first minus reactive. McNemar's test fits
because each instance is its own control, and its power depends on the number
of discordant pairs rather than on $n$, so we report the interval even when the
test is not significant. Only instances completed by both arms enter the
paired analysis.

As secondary measures we report, for Arm B, the gate-accept rate, C2P,
Valid-BRT, and resolved-rate among accepted instances, along with the L0--L4
distribution of the submitted tests, which is computed offline and never gates
a run. For both arms we report model calls, iterations per phase, tokens, and
how each phase ended (voluntary submission or a forced one at the iteration
cap). The model is free, so dollar cost is zero; model calls were the scarce
resource and stand in for cost.

RQ2 is answered from runs already stored, with no new model calls. The two
questions about the gate use the nemotron-3-super sweep itself. Every test the
sweep produced carries an offline L0--L4 label, so we can count how many
resolved instances an L4-only oracle gate would have discarded, without
re-running anything, and the retry records show which instances the gate's two
retries recovered. The remaining variants (self-review of the test and of the
fix, adversarial verification after the fix, and best-of-$N$ test selection)
were only run earlier, with Claude Sonnet 4.6 on the development set and the
same pipeline code. That set is small and non-random, so we report those
comparisons with their $n$ \ph{per variant} as case-level evidence from a
different model.

RQ3 records the stage at which each trajectory ends: no terminal submission
within budget, a submitted test that does not fail on the buggy revision, a
fix that does not resolve, or a resolved issue. The nemotron-3-super runs from
RQ1 supply one hosted model. Four local models served through Ollama
(qwen2.5-coder 7B and 14B, qwen3.5 9B, and mistral 7B) ran the test-phase
agent on development-set instances, almost all of them astropy, and
qwen2.5-coder 14B also ran the full deployable pipeline.

\subsection{Infrastructure and Reproducibility}
\label{sec:exp-budget}

Each instance runs in its own SWE-bench Docker image, and all agents working
on an instance share one persistent container so that each tool call avoids
container start-up. Environments we built locally installed current versions
of unpinned dependencies, and that broke 7 of the 60 builds; for those
instances we used SWE-bench's prebuilt images, re-tagged locally, with their
digests recorded in \texttt{sample\_lite\_env.json}. Wall-clock time was not
the limit. The daily call cap and the provider's capacity were: a unit that
failed on a provider error left no record, was retried later, and its calls
still counted against that day's cap.

Every agent run appends one record to an append-only store
(\texttt{results.jsonl}) holding its budgets, token counts, stopping cause,
serving provider, and verdict. Each instance also gets a unit record that ties
the arms together. Transcripts are kept under \texttt{runs/} and harness logs
under \texttt{logs/}. The frozen sample, the environment record, the run store,
and the code are published in the repository at commit \ph{freeze commit}.
