\section{Approach}
\label{sec:approach}

\subsection{Pipeline Overview}
\label{sec:method-overview}

TDBF runs two agents in a fixed order (Figure~\ref{fig:pipeline}). The test
agent reads the issue, explores the buggy repository, and submits a bug
reproduction test. A gate then runs that test on the buggy revision. If the
test fails at an assertion, the gate accepts it and hands it to the fix agent,
which edits the source until the test passes and then submits a patch. If the
test passes, errors, or crashes before asserting, the gate sends the test agent
back with feedback, and after two retries it rejects the instance, which then
gets no fix at all.

The order is enforced by the architecture. The fix agent is constructed only
after the gate has accepted a test, so no repair can begin until a failure has
been executed and observed on the buggy code. The gate's decision also uses
nothing a deployed system would lack, which is the subject of the next
subsection.

\subsection{The Gold-Free Invariant}
\label{sec:method-goldfree}

No agent ever holds a tool that can observe the reference (``gold'') patch,
the tree with that patch applied, or the benchmark's held-out tests. An agent
receives four fields of an instance: its identifier, the repository, the base
commit, and the issue text. Each agent's tools come from a fixed allowlist, and
an assertion rejects any tool outside that list when the agent is built. The
reference data is used after a run has ended, to score the
patch and to label the test (Section~\ref{sec:method-levels}); no label or
verdict flows back into a run.

The invariant decides what kind of result the paper reports. A pipeline whose
accept decision consults the reference patch is an oracle study, and it cannot
be deployed, because a real bug arrives without its fix. We built such an
oracle variant early on, gating on the L4 label; we keep it as a ceiling
for comparison, and every result for the test-first arm comes from the
gold-free gate.

\subsection{Agent Runtime and Tools}
\label{sec:method-runtime}

Both agents run in one vendor-neutral tool-use loop. On each turn the model
returns tool calls, the runtime executes them and appends the results, and the
loop continues until the agent calls its terminal tool (\texttt{submit\_test}
or \texttt{submit\_fix}), answers without calling any tool, or exhausts its
iteration or token budget. An agent that reaches its iteration cap without
submitting gets up to three closing turns in which it must call its terminal
tool with its best result, so a stalled run still yields an artifact; we
record such runs as forced submissions.

Every RQ1 run uses the free model nemotron-3-super, which we reach through
OpenRouter's OpenAI-compatible API (Section~\ref{sec:exp-arms}); the runtime
also has Anthropic and Ollama clients, used for the development runs and the
local models. On the OpenAI-compatible and Ollama paths, when a model writes a
tool call into its reply as text instead of sending a structured call, the
runtime recovers the call and executes it, provided it names a real tool. This
recovery was active in every RQ1 run, in both arms. The Anthropic client has
none. Recovery helps a model that formats its calls badly, so it may
make the open-weight models look better than they are, and we report it for
that reason.

Each phase works in one persistent Docker container per instance, built from
the SWE-bench image, so the many tool calls of a run pay the container's
start-up cost once. Table~\ref{tab:tools} lists the tools. Framework set-up
code, such as the Django bootstrap, is prepended to every test automatically,
so the agent writes the test logic and nothing else. The fix agent's \texttt{run\_brt}
takes no arguments: the accepted test is fixed when the tool is built, so the
agent can run the test but has no way to weaken it.

\subsection{Phase 1: Test Generation and the Acceptance Gate}
\label{sec:method-phase1}

The test agent's prompt asks for one pytest test that fails on the buggy code
at an assertion reflecting the issue, and that would pass once the bug is
fixed. The agent cannot run fixed code, so it has to reason from the issue
about the correct behaviour. The suggested workflow is to locate the code,
observe the actual buggy behaviour with \texttt{run\_python}, write the test,
and iterate with \texttt{run\_test} until the test fails at its assertion; the
agent decides the specifics and when to stop.

The gate re-runs the submitted test on the buggy revision, in the same live
container the agent worked in, and accepts it when the test fails and the
failure is not a crash. The second condition is needed because pytest reports a test
that fired its assertion and a test that crashed before reaching it with the
same exit status. A crash, such as an import error or a call to an API that
does not exist, fails in the same way on fixed code, so the test can never
pass there. We parse the output for assertion evidence first (an
\texttt{AssertionError}, a rewritten bare \texttt{assert}, or pytest's
\texttt{Failed:}) and look for a crash only when none is found. Searching for
exception names first had misread a valid test as a crash, because its own
assertion message printed labelled expected and actual values.

A test the gate accepts is labelled L3 or L4 offline (Table~\ref{tab:levels}).
Telling those two apart requires the fixed tree, so a deployable pipeline has
to attempt a fix from L3 tests as well, and some of those fixes succeed. When
a test is not accepted, the agent restarts from a fresh conversation, up to two
times, with feedback derived only from the buggy-side outcome: the test passed,
errored, crashed before asserting, or was never submitted. The feedback includes
the previous test. If the third attempt also fails the gate, the instance is
rejected and no fix is attempted.

\subsection{Phase 2: Fix Generation}
\label{sec:method-phase2}

The fix agent receives the issue and the accepted test, and runs in a new
container on the buggy tree. Its prompt presents the test as a guide rather
than as the definition of success, since the test may assert a wrong value, and
names the root cause described in the issue as the real target. The default
rule is to submit once \texttt{run\_brt} passes. A bail-out rule allows a
submission without a passing test only when the agent has concrete evidence
that the test itself is wrong, and the prompt says explicitly that a hard fix
is not such evidence. The prompt also warns that existing tests may already
fail for unrelated reasons, asks the agent to run the single test file nearest
its change, and tells it not to revert an edit that makes the test pass unless
it has found a regression that its own edit caused.

When the agent submits, the patch is the \texttt{git diff} of the tracked
source tree. The test file is untracked, so it never enters the patch. The
patch is then scored offline (Section~\ref{sec:exp-metrics}).

\subsection{The Reactive Baseline}
\label{sec:method-baseline}

The reactive arm runs the same fix agent with no test phase and without
\texttt{run\_brt}. Its tool set is derived in code as the fix agent's set minus
that one tool, so the two cannot drift apart. Its prompt was written line for
line against the test-first fix prompt: the sentences about the test are
removed and nothing else changes. The descriptions of \texttt{submit\_fix} and
\texttt{revert} likewise lose their references to the test, and an offline
check asserts that the shared lines stay identical. The baseline therefore receives the issue text, the repository, and
the repository's own tests through \texttt{run\_tests}, as the test-first arm
does. Model, budgets, container image and scoring are the same
(Section~\ref{sec:exp-arms}).

\subsection{Outcome Taxonomy and Metrics}
\label{sec:method-levels}

We label every submitted test by its outcome on the buggy and on the fixed
revision (Table~\ref{tab:levels}). Only L4, a test that fails on the buggy code
and passes once the reference patch is applied, is a valid reproduction test;
in SWE-bench terms it is fail-to-pass. The labels are computed offline, after a
run, and never gate anything at run time.

\begin{table}[t]
  \caption{Levels of a generated test, by its outcome on the buggy and the
  fixed revision.}
  \label{tab:levels}
  \small
  \begin{tabularx}{\linewidth}{@{}lllX@{}}
    \toprule
    Level & Buggy & Fixed & Meaning \\
    \midrule
    L0 & absent & -- & No test submitted, or it could not be collected \\
    L1 & pass & -- & Does not reproduce the bug \\
    L2 & error & -- & Breaks before running, e.g.\ during collection or set-up \\
    L3 & fail & not pass & Reproduces a failure, but not the one the reference fix addresses \\
    L4 & fail & pass & Valid reproduction test (fail-to-pass) \\
    \bottomrule
  \end{tabularx}
\end{table}

From the labels we compute
\begin{equation}
  \mathrm{C2P} = \frac{|L4|}{|L3| + |L4|}, \qquad
  \text{Valid-BRT} = \frac{|L4|}{N},
\end{equation}
where $N$ is the number of instances. C2P asks how often a test that
reproduces some failure reproduces the right one. For the whole pipeline we
report the gate-accept rate, the resolved-rate among accepted instances, and
their product, the overall resolved-rate. An instance is \emph{resolved} when
every held-out FAIL\_TO\_PASS test passes and every PASS\_TO\_PASS test still
passes under the submitted patch.
