\section{Context and Motivation}
\label{sec:intro-context}
Agentic AI systems are now used daily to write and maintain production software.
Practitioners, however, are still establishing how to use them well; industry
accounts of building complete systems with heavy AI assistance report that the
outcome depends less on the model than on how the work is
structured~\cite{Akita2026MethAI}. That observation has a technical reading.
Software construction is not a single activity but a sequence of distinct phases
--- planning, implementation, debugging, review, and maintenance --- each with
its own goals, its own notion of correctness, and its own failure modes. A
general-purpose language model that performs well in one phase offers no
guarantee of doing so in another, which makes phase-specific study of agent
behaviour necessary rather than optional.

This thesis concerns the debugging phase. Debugging is expensive: before a single
line of a fix is written, a developer typically writes or reads a bug report,
gathers diagnostic information, constructs a test case that exhibits the failure,
and investigates the root cause. That workflow is repetitive, time-consuming, and
a well-recognised bottleneck in development cycles --- which makes it an
attractive target for automation, and a demanding one.

Recent advances in large language models (LLMs) and agent-based software
engineering systems have shown promise on tasks such as code generation, test
generation, and program repair. Real-world bug fixing nonetheless remains
difficult. On SWE-bench, a benchmark of 2,294 genuine GitHub issues introduced by
Jimenez et al.~\cite{Jimenez2023SWEbench}, the SWE-agent system of Yang et
al.~\cite{Yang2024SWEagent} resolves approximately 12.5\% of issues --- a
state-of-the-art result at the time of publication, and still a reminder of how
far automated repair is from reliability on real code.

One finding from recent work is particularly relevant to that gap: the presence
of a \emph{Bug Reproduction Test} (BRT) --- a test that fails on the buggy
revision and passes once the bug is fixed --- materially improves repair
outcomes. In a study on Google's internal codebase, Cheng et
al.~\cite{Cheng2025Agentic} showed that supplying an automated program repair
system with high-quality BRTs increased the proportion of bugs reaching a
plausible fix by 30\%.

That finding has not, however, been carried into agent \emph{architecture}.
Contemporary repair agents remain reactive: they attempt a patch first and
validate afterwards, so the test, when it appears at all, arrives as
after-the-fact confirmation rather than as a constraint on the search. This
thesis reverses that order, requiring an agent to produce and validate a targeted
reproduction test from the bug report and repository context \emph{before} any
fix is attempted --- mirroring test-driven practice in human development, and
using the agent's own code comprehension to sharpen the objective it is then
asked to satisfy.

The rationale is that a reproduction test functions as an executable
specification of the failure, constraining the space of acceptable patches. By
forcing reproduction first, the fix stage receives an earlier and sharper
feedback signal than post-hoc validation can provide, which should reduce
unfocused edits and improve repair precision.

\section{Problem Statement}
\label{sec:intro-problem}
Current agents are strucutured to resolve the bug right away, without holding a lot of specifications of the failure. That is the gap we working on. How do we engineer agentic systems that fix more bugs by adopting a test-first order rather than reactive validation? The thing with reactive agent is that they have no exectable specifications, the agent relies on its reading of the issue, which can lead to misinterpratation, unfocused edits, regressions in unrelated code, and a self-declared stopping criterion. The TDD comes to guide the LLM on throught those issues, so it can always test if what it's being changed its being done on the right place and not breaking other parts of the code. Test generation from LLM is well studied, and APR is well stablished, however it was not done all in one unique pipeline, rather are different systems that work separatelly. We focus on how making TDD mandatory for bug fixing in one agentic system only can make a difference.

The literature establishes that test-generation quality, repair capability, and
orchestration each affect how many real-world issues an agentic system
resolves~\cite{Meng2024Empirical}. It does not establish how those components
should be composed, nor in which order a practitioner should run them. The three
questions below move from the overall effect of ordering, to the properties of
the test artifact through which any such effect must be carried, to the pipeline
characteristics that sustain it under a fixed budget.

\paragraph{RQ1 --- Does a test-first agentic pipeline, in which repair is
withheld until a generated test has been observed to fail on the buggy revision,
resolve more real-world issues than a matched reactive pipeline?}
This question is answered by a paired comparison on SWE-bench Lite in which every
sampled instance is processed by both arms under the same model, tool set,
iteration and token budgets, container, and scoring harness; the arms differ only
in the presence of the reproduction phase and of the tool that executes its
output. \emph{Reactive} denotes the prevailing design, exemplified by
SWE-agent~\cite{Yang2024SWEagent}, in which an agent may run tests but is under
no obligation to establish a failing one before editing begins. The primary
outcome is resolved-rate: the benchmark's held-out failing tests pass and its
previously passing tests are preserved.

\paragraph{RQ2 --- Which properties of a generated bug-reproduction test predict
whether the fix it guides resolves the issue?}
This question is answered offline, over the stored artifacts of every run, by
relating measurable properties of each generated test---assertion density,
length, whether assertions check exact values or only that an exception is
raised, determinism under repeated execution, and overlap with the lines the
reference patch modifies---to whether the fix produced under it resolved the
issue. That reproduction-test quality matters is already
established~\cite{Cheng2025Agentic}; RQ2 asks which properties carry the effect.
Because the analysis runs offline and after the fact, it may consult the
reference patch, which no agent at any point may.

\paragraph{RQ3 --- Which pipeline and orchestration characteristics improve fix
quality and reliability under a fixed budget?}
This question is answered by ablations over the test-first pipeline: the
criterion by which a generated test is accepted without access to the reference
patch, the per-instance attempt budget, agent self-review of the test and of the
fix, post-fix adversarial verification, and best-of-$N$ test selection. The
primary outcome is the change in resolved-rate attributable to each variant,
reported against its measured cost. Two of these ablations produced negative
results; they are reported as findings rather than omitted.

Two conditions bound the scope of all three questions rather than forming
questions of their own. The first is model capability: the pipeline presupposes
an agent able to sustain an autonomous tool-use loop to a terminal submission,
and Section~\ref{sec:results-weak} reports the configuration in which that
presupposition fails. The second is the absence of a run-time oracle. No agent
ever observes the reference patch, the fixed revision, or the benchmark's
held-out tests (Section~\ref{sec:method-goldfree}), so every acceptance decision
taken inside the pipeline rests on evidence a deployed system would also have ---
a constraint that shapes what RQ3 can ask and what RQ1 can claim.
