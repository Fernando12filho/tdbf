You annotate a GitHub bug report. Mark the parts of the text that convey each type of information below. Copy every span VERBATIM from the report: exact characters, including code, punctuation and line breaks. Do not paraphrase, summarise or fix typos. A span can be a whole sentence, part of a sentence, or a code block. Leave text that conveys none of these types unmarked (greetings, frustration, template headings, discussion that adds nothing). Mark the same text with two types only when it clearly conveys both.

Rules that decide the hard cases. Follow them strictly; when in doubt, leave text unmarked.

BUG_AFFECTED_AREA (LINE, FUNCTION, FILE, GENERIC) marks ONLY text where the reporter says or clearly implies WHERE IN THE PROJECT'S CODE THE BUG LIES OR WHAT CODE CAUSES IT. Typical forms: "This is caused by X", "the problem is in X", "the culprit seems to be X", "X does not handle Y", "Looking at the source, X ...", or a link to a source line or file given as the place of the defect.
- Do NOT mark a function, class or file just because it is named or called. Names that appear in reproduction code, in a traceback, in the title, or in a description of what the user did are NOT affected areas.
- A traceback is BUG_OBSERVED_BEHAVIOUR, never an affected area.
- Use LINE for a specific line or line link, FUNCTION for a named function or method identified as the cause, FILE for a named file or module identified as the cause, GENERIC when the reporter points to a part of the code without naming it ("the internal logic", "the caching layer").
- Most bug reports have NO affected area. Expect it in roughly half of reports or fewer.

BUG_EXPECTED_BEHAVIOUR marks ONLY text that states or shows the CORRECT outcome: what should happen, what the output should be, what was expected, or how it behaves when it works ("should return", "I expected", "Expected behavior:", "instead of X it should Y", "in version N it printed Z", an assertion or output that shows the correct value).
- Saying that something is wrong, broken or surprising is NOT expected behaviour; that is observed behaviour or summary.
- A section heading such as "Expected behavior" alone is not a span; mark the content under it.

BUG_REFERENCE marks ONLY explicit pointers to something outside the report: links (URLs), issue or pull-request numbers (#1234, "ticket 8060"), commits, Stack Overflow questions, documentation pages. Links used as the location of the defect are BUG_AFFECTED_AREA instead. A code name in prose is not a reference.

BUG_REPRODUCTION_STEPS marks the code or steps that trigger the bug, without the error output itself.

BUG_OBSERVED_BEHAVIOUR marks the wrong outcome: error messages, tracebacks, wrong output, or a description of what goes wrong.
