Test-writing architectures

development studies · Phase A only
Every architecture we tried for the test-writing phase (Phase A), on the same bugs, against the old agent: TDBF's single test-writing agent. These are development results on small bug sets, used to choose an architecture; this is not the evaluation. A test is L4 (valid) if it fails on the buggy code and passes once the real fix is applied, and L3 if it fails on both (it checks the wrong thing). Each study fixed its rule before running: an architecture is adopted only with more L4 than the old agent, no more L3, and cost per valid test at most 1.5× the old agent's. Rows still running show how many bugs are done.

How to read this
  • No architecture so far has beaten the old single agent with the same writer model on clean bugs: the procedure agent (strict 15, soft 20 vs 21), scouts v1 (19 vs 21), scouts v2 (16 vs 17) and the blackboard (15 vs 17 on the fresh bugs) all fail the rule. Every difference is within run-to-run variation.
  • The blackboard's 23 vs 21 on the 30 development bugs passes "more L4" and "no more L3" but costs 2.2× per valid test; three of its five gains are the L3 cases judge v2's rules were derived from, so it most likely reflects judge v2 on its own development bugs, not the board.
  • The judge inside the writer's loop works mechanically (it objects and the writer revises), but did not turn any L3 into L4. Half of the L3 tests follow the issue and fail only because the benchmark's fix differs from what the issue asks, which no gold-free check can see.
  • On the fresh bugs the old agent already reaches 17/20, so small sets leave little to win. The final evaluation (SWT-bench Lite, against ReProAgent with the same model) and the bugs the single agent fails there are where multi-agent designs get a fair test.
Plans and analyses (rules fixed before each run): studies/scouts/plan.md, plan_v2.md, plan_blackboard.md; results/dev_comparison.md, v2_comparison.md, gate2_l3_match_arm.md (branch agent/scouts).
