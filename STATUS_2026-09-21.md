**21 September 2026** · data freeze **Thu 24 Sep** · submission **Sun 27 Sep**

> as findings.

---

## 1. What the project is

TDBF (Test-Driven Bug Fixing) studies an **agentic** approach to fixing real
GitHub issues from SWE-bench Lite. Given an issue, an LLM agent:

1. reproduces the bug and writes a **Bug Reproduction Test (BRT)** that fails on
   the buggy revision and would pass once fixed, then
2. edits the source until that test passes.

The contribution is twofold: the *agentic* framing — the model drives its own
tool-use trajectory rather than following a fixed code loop — and a way to decide
a test is good enough to act on **without ever consulting the gold patch**.

Two anchors run through all of it:

- **BRT levels L0–L4.** Only **L4** (fails on buggy → passes on fixed) is a valid
  reproduction test. The headline test metric is **C2P = L4 / (L3 + L4)**.
- **The gold-free invariant.** No agent ever receives a tool that can observe the
  gold patch, the gold-fixed tree, or the held-out tests. Gold is an *offline
  measurement instrument only*. This is enforced in code by a per-role allowlist
  (`assert_gold_free` and siblings) that raises at construction time, not by
  convention.

## 2. What we are measuring

### Research questions

| | Question |
|---|---|
| **RQ1** | **Ordering.** Does test-first — withholding repair until a test is *observed* to fail on the buggy revision — resolve more issues than a matched reactive arm? |
| **RQ2** | **Orchestration.** Which pipeline characteristics improve fix quality under a fixed budget? Ablations, negatives included. |
| **RQ3** | **Open-weight models.** Can they sustain the pipeline, and at *which stage* does the trajectory break down — terminal submit, reproduces on buggy, or resolves? |

### The two arms (the RQ1 comparison)

Both arms use the same model, the same budgets and the same tools **except one**:

- **Arm A — reactive baseline.** No Phase A, and `run_brt` removed from the fix
  agent's toolset (it keeps `run_tests`). The agent repairs directly.
- **Arm B — test-first.** The deployable pipeline: write a BRT, gate it
  gold-free, then repair against it.

The arms are paired per instance and run back-to-back in a seeded random order,
so the comparison is within-instance. A unit is recorded only when **both** arms
finish, because McNemar uses complete pairs.

### The gate that makes it deployable

Arm B accepts a test iff it **reached its assertion and failed there** on the
buggy tree:

```
outcome_buggy == "fail" and failure_reason != "runtime"
```

This is the crux of the gold-free claim, and both halves were learned the hard
way:

- pytest exit code 1 conflates *an assertion that fired* with *a test that
  crashed before asserting*. A crash fails identically on fixed code, so it can
  never be L4 — accepting it inflates the gate.
- the criterion is `!= "runtime"`, never `== "assertion"`. A bare `assert x == y`
  with no message emits no `AssertionError:` line, so the strict form rejects
  perfectly valid reproductions.

## 3. Results so far

### 3.1 Frontier reference — Claude Sonnet, n = 14

A stored reference point, **not** a headline result: non-random development set,
pilot quality.

| metric | value |
|---|---|
| gate accepted | 14 / 14 |
| resolved | 10 / 14 |
| C2P | 13 / 14 |
| total cost | $2.73 |

Two things this established. First, **fix outcomes are not fully deterministic** —
of 15 repeat (instance, model) pairs, one disagrees. A single run per arm carries
noise, which is why RQ1 will be reported with a bootstrap CI rather than a point
estimate. Second, **the gold-free gate is not merely a degraded L4 oracle**: runs
accepted on an L3 test have gone on to resolve, so gating on L3∪L4 gained fixes
that a strict L4 gate would have discarded.

### 3.2 Capability probe — nemotron-3-super-120b (free), today

There is no paid API budget, so RQ1 must run on a free model. Whether any free
model is capable enough was the open risk gating the whole sweep. Probe design:
3 development instances, Arm B only.

| instance | BRT | iters | label | gate | fix stop | iters | resolved | calls |
|---|---|---|---|---|---|---|---|---|
| astropy-12907 | submit | 10 | **L4** | accept | max_iterations | 30 | **yes** | 43 |
| astropy-14182 | submit | 14 | **L4** | accept | submit | 16 | no | 30 |
| astropy-14365 | submit | 11 | **L4** | accept | submit | 6 | no | 17 |

**Gate 3/3 · C2P 3/3 = 1.00 · Valid-BRT 3/3 · resolved 1/3 · 90 calls · 0 throttles · $0.00**

**Reading it.** Every test was submitted voluntarily — no forced submissions —
reached an assertion on the buggy tree, and independently scored L4 against the
gold-fixed tree. The risk that no free model could sustain the pipeline is
retired.

**The two non-resolutions are not capability failure.** Both report
`applied=True`, `PASS_TO_PASS fail=0`, `FAIL_TO_PASS 0/1`: a valid test, a clean
patch that breaks nothing, which passes the reproduction test and still does not
satisfy the held-out test. This is the **verification gap** — passing a BRT is
*necessary but not sufficient*. It is the same dominant failure mode already
documented on Sonnet, which makes it a consistent property of the method rather
than an artifact of using a free model.

**Caveats, stated plainly.** n = 3, development set, astropy only — the repo this
project has exercised most. C2P 1.00 over three instances is **not** evidence
that this model outperforms Sonnet.

## 5. Schedule, honestly

Phase 3 (the sweeps) was planned for Fri 18 – Wed 23. **It has not started**; the
last experimental run recorded was 16 September. Roughly two and a half days of
running remain before the freeze.

Throughput, measured rather than estimated: Arm B averaged **30 model calls**
(range 17–43) at ~15–18 minutes per instance. A paired unit is therefore ~45–50
calls and ~25–30 minutes, so the 950/day cap allows **~19–21 pairs/day** — with
wall-clock, not quota, as the binding limit.

Running continuously through Tuesday and Wednesday puts **n ≈ 40–55** within
reach of the 56 runnable instances. The original n = 60 is not achievable.

**Pre-registered now, before the data exists:** instances run in frozen-file
order, and whatever n completes by the freeze is what gets reported — so the
analysed subset is a *prefix* of the frozen sample, not a selection of whichever
units happened to look good.

The real critical path is **writing**, not data. The paper was converted to ACM
`acmart` format today and its sections are still thin. A smaller n with finished
sections is worth more than a larger n without them.
